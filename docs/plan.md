# AuroraBot 里程碑与编码计划

日期：2026-11-01；实现核对基线：`1bf1f4b`；纳入直接交流与世界输入的设计决策。

设计基线：[初期设计 v0.2.3](aurorabot-design-v0.2.3.md)、[公共 ID 目录 v0.2.3](aurorabot-id-catalog-v0.2.3.md)、[执行包拆包评估](aurora_agent_extraction_assessment.md)。

本计划细化设计中的 M0–M4，作为任务拆分、编码顺序和阶段验收依据。任务编号仅用于计划追踪，不是公共 ID。下文模块路径是建议的代码落点，按实际复杂度拆分，不要求提前创建全部文件。

## 1. 实施基线与范围

M0、M1、M2 已完成。core 的登记、ctx、订阅、持久化、连接调用与五阶段生命周期，`aurora_config` 的配置声明与加载，`aurora_control` 的执行契约与控制组合，`aurora_agent` 的 ReAct、模型调用、工具执行与运行调度，以及 `aurora_bot` 的默认装配与 CLI 运行入口均可使用；M2.8 于 2026-10-31 通过整体验收。五个示例的启动方式见 [示例指南](../examples/START.md)。

M3 进行中：已有本机 HTTP/WS ctx 传输及 Python 客户端，M3.4 提供当前协议的按需契约生成，M3.5 提供共享 TS client 的访问、订阅、主动关闭与重连刷新。M3.6 已交付目标 bot 的直接交流、接纳回执、重复请求处理、查询和指定运行取消，首版 OpenTUI 已提供交流/只读状态页、工具活动与取消，并支持本地连接设置、页面与工具展开偏好。后端配置编辑、ctx 写操作、完整联调及浏览器/远程访问边界仍待交付。M4 扩展分支未进入实现，M4-W 正式承接世界输入与 cadence。执行包已按 control、agent、bot 分层，独立 harness 的边界与剩余工作见[拆包评估](aurora_agent_extraction_assessment.md)。下文任务表保留各阶段的交付范围，不表示所有条目均未开始。

两条输入路径按交流性质划分：面对面交流通过产品入口向目标 bot 提交引导；外部消息与环境变化经 `world → cadence` 形成引导。首版默认 Panel/TUI/CLI 使用直接交流，外部来源进入 world；平台本身不决定永久路由。两条路径复用同一 AgentRuntime，直接交流不要求安装或启用 world/cadence。

实施必须保持以下边界：

- core 维护通用登记、ctx、连接、订阅、最小调用和生命周期；执行契约与控制组合由 `aurora_control` 提供，ReAct、模型、工具与运行调度由 `aurora_agent` 提供，产品装配由 `aurora_bot` 提供。
- 定义 ID、组件实例、状态值、事件实例分别管理；命名空间不是内部权限边界，不从 ID 路径推导执行顺序、URL 或文件位置。
- 插槽接收方判断兼容性，按需使用类型、签名或 schema；不要求所有连接具备独立契约文件。
- bot 组件通过 ctx 读写业务数据，连接握手交换地址与可选 schema，执行只传递运行和调用身份；等待执行确定完成，订阅用于观察或组件主动选择的触发方式。
- CLI/API 为可选宿主。缺席时保留相关声明、标记未连接并告警；实际调用缺失目标必须明确失败。
- Python 插件、CLI、client 共用 ctx 访问语义；client 沿用已有 core ctx 操作 ID，API 只传输实际开放的数据。
- 正常退出先停止新工作，再结束在途工作和最后写入，最终落盘后关闭存储。最终落盘由宿主保证。
- 单租户、单后端可连接多个界面；TUI/Panel 的视图偏好留在各自本地，插件发现和装配留在后端。

初期不纳入多租户隔离、插件热插拔、恶意插件沙箱、通用远端 operation 分发、完整执行图语言、全量契约生成、复杂秘密管理、完整 MCP 和 `aurora_playground`。

## 2. 里程碑与依赖

| 里程碑 | 可演示成果 | 进入条件 | 完成条件 |
| --- | --- | --- | --- |
| M0 骨架与登记（完成） | 宿主发现插件、登记定义，输出连接诊断 | 现有工作区 | ID、自举、发现及可选宿主行为通过验证 |
| M1 微内核可用（完成） | CLI 操作 ctx、观察变化，退出后恢复状态 | M0 | 显式状态操作、连接调用、异步落盘及生命周期闭环 |
| M2 最小 bot（完成） | 单模型流式对话、工具循环、取消与恢复、CLI 提交观察 | M1；ModelClient 协议已具备 | 默认装配可运行，完成/取消/失败可区分，SDK 不泄漏 |
| M3 API、client 与 TUI | TUI 连接后端，操作 ctx 并完成对话交互 | M1 支撑传输；M2 支撑对话 | 共享访问语义、访问边界、断线恢复及 OpenTUI 交互可验收 |
| M4 能力扩展与产品入口 | 世界输入与 cadence、多模型、agent、最小 MCP、Vue Panel、静态站点 | 按扩展分支依赖进入 | 各分支独立验收，默认装配与多客户端场景回归通过 |

关键路径：`M0 → M1 → M2 → M3 直接交流与工作台 → M4 集成验收`。当前已完成 M2 和 M3 的共享 client、直接交流基础，接续 M3.7。M4-W 的实现与 M3 分开验收，排在工作台之后，不成为直接交流的前置依赖。

允许独立推进的工作：

- M1 的 ctx 访问语义确定后，可推进 M3 的 API/client ctx 路径；不等待全部 bot 能力。
- ModelClient 类型与假模型可在 M1 期间准备，真实装配与生命周期接入依赖 M1。
- M4 多模型、MCP 依赖 M2；Panel 依赖 M3 共享 client；静态站点可先建立独立构建入口，使用说明随已验收行为补齐。
- M3.6 已实现直接交流回执与取消关联；ctx 查看、配置、订阅及连接状态可独立推进。
- M4-W 依赖 M1 的状态与生命周期、M2 的 AgentRuntime；两条输入路径并存验收复用 M3.6，复杂聚类、调度和真实平台适配不纳入首个 world/cadence 切片。

每个任务按一个可独立验证的行为切片组织。实现、必要测试和实际接口说明一起交付；较大任务拆成数个小提交，不集中堆积暂存区。阶段验收以可观察行为为准，不以公共 ID 数量或空文件数量为准。

D10 已由 M3.6 落实：面对面交流经 bot 的 conversation 端点提交至目标实例，复用既有 run 操作与 AgentRuntime；界面围绕长期存在的 bot 展示交流、运行和工具活动，不提前引入多会话上下文隔离。空闲时可启动运行，运行中接纳引导，保留当前 loop；停止针对指定 instance_id/run_id，界面断开仅停止观察。回执按 session_id/instance_id/request_id 去重，重启拒绝旧会话；查询关联引导和运行句柄。接纳不等于完成，不通过通用 ctx 写入隐式触发业务，也不新增 conversation/send、conversation/cancel 同义操作。具体信封、容量与错误边界见[设计第 10.2 节](aurorabot-design-v0.2.3.md#102-界面动作边界)。

## 5. M1：ctx、持久化、连接调用与 CLI（完成）

| M1.2 变化与事件订阅 | core 的 `events.py` 与 ctx 订阅；过滤、订阅句柄、取消、监听器异常处理 | M1.1 | 变化只来自成功的显式修改；取消后行为明确；监听器失败不破坏已提交状态；退出无订阅泄漏 |
| M1.3 异步持久化与恢复 | core 的 `persistence.py`；待写入安排、合并、恢复和显式 flush；实现 D03 选择的最小存储方案 | M1.1、D03 | 更新及删除可恢复；恢复失败可诊断；落盘期间新增修改不被错误标为已持久化；不序列化运行时连接 |

| M1.5 hook 连接与最小调用 | core 的 `hooks.py`、`invocation.py`；实例连接、接收方兼容判断、排序、必要的异步调用和异常传播 | M0.5、D05 | 描述不同但兼容可连接；无独立 schema 的约定连接可执行；明确不兼容被拒绝；不可调用项不能当 operation 执行 |
| M1.6 生命周期与退出 | core 的 `lifecycle.py`；prepare/start/stop、部分启动清理、依赖关闭、宿主最终 flush | M1.2–M1.5、D06 | 最后 stop 写入可恢复；禁用某个可选 handler 不跳过最终 flush；清理与落盘失败明确报告，不能假报正常退出 |
| M1.7 CLI 基础入口 | cli 的 `commands.py`、`main.py`；命令接收、帮助、ctx get/set/delete/list/watch、run、启动前预配置和参数校验 | M1.1、M1.2、M1.6 | argv 转为既有接口调用；watch 退出取消订阅；CLI 不导入 bot；配置在 prepare/start 所需时点生效 |
| M1.8 微内核集成验收 | `tests/e2e/` 的最小宿主和 CLI 场景；补充并发写入与关闭故障覆盖 | M1.7 | 写入→订阅→停止时写入→flush→重启读取闭环通过；无业务包时 core 可运行 |

CLI 的 M1 场景以当前宿主进程为操作环境；不隐含跨进程共享内存或另起一个 bot 后端。面向已运行后端的远程交互随 M3 连接方案确定。

必须覆盖的关闭序列：停止接收新工作 → 在途工作完成或取消 → 停止状态写入来源 → 最终 flush → 关闭存储与剩余资源。测试记录实际顺序，而非仅断言 stop 被调用。

### 8.5 M4-W：世界输入与最小 cadence

## 11. 接续队列与提交粒度
