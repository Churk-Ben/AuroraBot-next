# AuroraBot 里程碑与编码计划

日期：2026-10-29  
设计基线：[初期设计 v0.2.2](aurorabot-design-v0.2.2.md)、[公共 ID 目录 v0.2.2](aurorabot-id-catalog-v0.2.2.md)。

本计划细化设计中的 M0–M4，作为任务拆分、编码顺序和阶段验收依据。任务编号仅用于计划追踪，不是公共 ID。下文模块路径是建议的代码落点，按实际复杂度拆分，不要求提前创建全部文件。

## 1. 实施基线与范围

仓库已经具备 `uv workspace`、`pnpm workspace`、五个 Python 包的 src-layout、共享 client 与四个应用的包声明，以及测试和脚本目录。Python 包目前仅有初始化文件，client 为占位导出；业务实现、应用入口、测试与检查脚本仍需建设。因此 M0 仅有目录与包声明部分具备基础，不视为整体完成。

实施必须保持以下边界：

- core 维护通用登记、ctx、连接、订阅、最小调用和生命周期；ReAct、工具、选择、并行、循环等控制逻辑由 bot 插件提供。
- 定义 ID、组件实例、状态值、事件实例分别管理；命名空间不是内部权限边界，不从 ID 路径推导执行顺序、URL 或文件位置。
- 插槽接收方判断兼容性，按需使用类型、签名或 schema；不要求所有连接具备独立契约文件。
- CLI/API 为可选宿主。缺席时保留相关声明、标记未连接并告警；实际调用缺失目标必须明确失败。
- Python 插件、CLI、client 共用 ctx 访问语义；client 沿用已有 core ctx 操作 ID，API 只传输实际开放的数据。
- 正常退出先停止新工作，再结束在途工作和最后写入，最终落盘后关闭存储。最终落盘由宿主保证。
- 单租户、单后端可连接多个界面；TUI/Panel 的视图偏好留在各自本地，插件发现和装配留在后端。

初期不纳入多租户隔离、插件热插拔、恶意插件沙箱、通用远端 operation 分发、完整执行图语言、全量契约生成、复杂秘密管理、完整 MCP 和 `aurora_playground`。

## 2. 里程碑与依赖

| 里程碑 | 可演示成果 | 进入条件 | 完成条件 |
| --- | --- | --- | --- |
| M0 骨架与登记 | 宿主发现插件、登记定义，输出连接诊断 | 现有工作区 | ID、自举、发现及可选宿主行为通过验证 |
| M1 微内核可用 | CLI 操作 ctx、观察变化，退出后恢复状态 | M0 | 显式状态操作、连接调用、异步落盘及生命周期闭环 |
| M2 最小 bot | 单模型流式对话、一次工具循环、取消与恢复 | M1；ModelClient 协议可提前准备 | 默认装配可运行，完成/取消/失败可区分，SDK 不泄漏 |
| M3 API、client 与 TUI | TUI 连接后端，操作 ctx 并完成对话交互 | M1 支撑传输；M2 支撑对话 | 共享访问语义、访问边界、断线恢复及 OpenTUI 交互可验收 |
| M4 能力扩展与产品入口 | 多模型、agent、最小 MCP、Vue Panel、静态站点 | 按扩展分支依赖进入 | 各分支独立验收，默认装配与多客户端场景回归通过 |

关键路径：`M0 → M1 → M2 → M3 对话联调 → M4 集成验收`。

允许独立推进的工作：

- M1 的 ctx 访问语义确定后，可推进 M3 的 API/client ctx 路径；不等待全部 bot 能力。
- ModelClient 类型与假模型可在 M1 期间准备，真实装配与生命周期接入依赖 M1。
- M4 多模型、MCP 依赖 M2；Panel 依赖 M3 共享 client；静态站点可先建立独立构建入口，使用说明随已验收行为补齐。
- 界面提交/取消机制未决时，可以完成 ctx 查看、配置、订阅及连接状态；对话提交与取消联调必须等待相应决策。

每个任务按一个可独立验证的行为切片组织。实现、必要测试和实际接口说明一起交付；较大任务拆成数个小提交，不集中堆积暂存区。阶段验收以可观察行为为准，不以公共 ID 数量或空文件数量为准。

## 5. M1：ctx、持久化、连接调用与 CLI

设计对应：第 5、7.1–7.5、9 节；公共 ID 目录第 3、4 节。

| 任务 | 编码内容与落点 | 依赖 | 验收 |
| --- | --- | --- | --- |
| M1.1 显式 ctx 原语 | core 的 `ctx.py`；get/set/delete/list、状态项定义引用、业务定位和已配置校验；绑定既有 ctx operation ID | M0、D02 | 跨命名空间访问一致；外部原地修改读出值或写入参数不能改变内部状态；失败写入无部分变更 |
| M1.2 变化与事件订阅 | core 的 `events.py` 与 ctx 订阅；过滤、订阅句柄、取消、监听器异常处理 | M1.1 | 变化只来自成功的显式修改；取消后行为明确；监听器失败不破坏已提交状态；退出无订阅泄漏 |
| M1.3 异步持久化与恢复 | core 的 `persistence.py`；待写入安排、合并、恢复和显式 flush；实现 D03 选择的最小存储方案 | M1.1、D03 | 更新及删除可恢复；恢复失败可诊断；落盘期间新增修改不被错误标为已持久化；不序列化运行时连接 |
| M1.4 数据目录与存储接入 | 在 D04 选定包中实现目录分配和最小结构化存储接口；服务对象以运行时方式托管 | M1.3、D03、D04 | 目录映射受数据根约束；插件可自行管理数据库；数据库内容不强制镜像到 ctx；不新增未经确定的公共 ID |
| M1.5 hook 连接与最小调用 | core 的 `hooks.py`、`invocation.py`；实例连接、接收方兼容判断、排序、必要的异步调用和异常传播 | M0.5、D05 | 描述不同但兼容可连接；无独立 schema 的约定连接可执行；明确不兼容被拒绝；不可调用项不能当 operation 执行 |
| M1.6 生命周期与退出 | core 的 `lifecycle.py`；prepare/start/stop、部分启动清理、依赖关闭、宿主最终 flush | M1.2–M1.5、D06 | 最后 stop 写入可恢复；禁用某个可选 handler 不跳过最终 flush；清理与落盘失败明确报告，不能假报正常退出 |
| M1.7 CLI 基础入口 | cli 的 `commands.py`、`main.py`；命令接收、帮助、ctx get/set/delete/list/watch、run、启动前预配置和参数校验 | M1.1、M1.2、M1.6 | argv 转为既有接口调用；watch 退出取消订阅；CLI 不导入 bot；配置在 prepare/start 所需时点生效 |
| M1.8 微内核集成验收 | `tests/e2e/` 的最小宿主和 CLI 场景；补充并发写入与关闭故障覆盖 | M1.7 | 写入→订阅→停止时写入→flush→重启读取闭环通过；无业务包时 core 可运行 |

CLI 的 M1 场景以当前宿主进程为操作环境；不隐含跨进程共享内存或另起一个 bot 后端。面向已运行后端的远程交互随 M3 连接方案确定。

必须覆盖的关闭序列：停止接收新工作 → 在途工作完成或取消 → 停止状态写入来源 → 最终 flush → 关闭存储与剩余资源。测试记录实际顺序，而非仅断言 stop 被调用。

## 6. M2：ModelClient 与最小 ReAct bot

设计对应：第 7.3、7.6、8 节；公共 ID 目录第 5、6 节。

| 任务 | 编码内容与落点 | 依赖 | 验收 |
| --- | --- | --- | --- |
| M2.1 模型协议与假实现 | model_adapter 的 `protocols.py`、`models.py`；请求、响应、chunk、能力声明及工厂协议；测试中提供确定性假模型 | M0 登记基础、D07 | 流式文本、工具请求、无能力/失败路径均可离线驱动；公共协议不含 SDK 类型 |
| M2.2 默认装配与实例绑定 | bot 的 `assembly.py`、model_adapter 的工厂接入；装配资源、逻辑模型角色、实例连接、服务注入 | M1、M2.1、D03、D05 | 同一 ModelClient 定义可有不同实例；配置可恢复、连接对象不落盘；bot 无 CLI/API 实现依赖 |
| M2.3 LiteLLM 适配 | model_adapter 的 `adapters/litellm.py`；能力映射、非流式/流式转换、工具调用片段组装、超时、取消和连接释放 | M2.1、M2.2、D07 | 使用模拟 SDK 响应覆盖转换与异常；能力不足明确拒绝或按显式配置降级；SDK 对象不上泄 |
| M2.4 对话运行与状态 | bot 的 `conversation.py`；send/cancel 进程内操作、消息/运行定位、状态转移、事件关联与最终结果 | M2.2、D10 运行部分 | started 后恰有一个终态；completed/cancelled/failed 可区分；重复提交及取消竞态按确定语义处理 |
| M2.5 提示词与 ReAct 控制 | bot 的 `react/`、`resources/`；soul/react 资源、六个插槽及默认处理器；最小循环控制与终止限制 | M1.5、M2.4 | 无工具时结束，有工具时进入 act/observe 后再次 infer；达到轮次限制可解释地收束；循环不进入 core |
| M2.6 基本工具路径 | bot 的 `tools/`；工具注册、参数校验、before_call/after_call、结果与失败结构；先用确定性本地工具验收 | M2.5 | 未知工具/非法参数不执行；工具结果可进入下一轮上下文；失败、超时、取消不遗留悬挂运行 |
| M2.7 CLI 对话接入 | bot 声明 chat/cancel 命令，由 CLI 接收并绑定操作；流式输出和中断处理 | M1.7、M2.4–M2.6 | CLI 显示增量与终态；中断触发约定取消并清理；CLI 缺席时进程内运行仍可完成 |
| M2.8 最小 bot 验收 | `tests/contract/` 的模型与插槽边界，`tests/e2e/` 的默认装配、工具循环、取消、重启 | M2.3、M2.7 | 假模型场景无需网络/密钥即可重复；使用可用配置另做真实模型冒烟；两者结果分别记录 |

对话恢复至少验证消息和所选配置的恢复；进程重启时遗留的进行中 run 必须按明确策略处理，不能继续显示为仍在执行，也不承诺透明续跑。该策略随 M2.4 确定。

阶段演示：CLI 提交输入 → 模型返回工具请求 → 工具执行并记录观察 → 模型输出结果；另演示一次流式取消和一次工具失败。运行状态、事件和持久化结果互相一致。

| M3.6 界面动作联通 | 依据 D10 完成 client 与 bot 执行的最小关联；必要时由 bot 声明明确用途的端点并交给 API 接收 | M2.8、M3.5、D10 界面部分 | 提交和取消对应正确 run；不会因重连默默重复提交；仅实现选定机制所需接口 |
| M3.7 OpenTUI 基础界面 | TUI 的应用入口、连接状态、ctx 查看/操作、配置、默认键位、本地偏好；确认 OpenTUI 所需运行时与工作区兼容 | M3.5 | 终端启动、输入、错误反馈和退出可用；偏好不污染后端；UI 仅依赖 client 访问后端 |
| M3.8 OpenTUI 对话 | TUI 的对话视图、流式渲染、工具与运行状态、取消动作 | M3.6、M3.7 | 一轮对话和取消可操作；断线有明确反馈；终端恢复与连接清理正确 |
| M3.9 跨语言与联调验收 | `tests/contract/` 共用访问样例、client 测试与 TUI/后端集成场景 | M3.8 | Python 与 TS 对相同 ctx 用例结果一致；两个客户端观察同一后端变化；断线后可重新获得一致快照 |

API 和 client 的契约仅覆盖实际开放的数据与动作。取消本地订阅、关闭连接和取消 bot 运行是不同操作，分别定义并验证。事件序号用于识别顺序或缺口时，必须明确其作用域；不以序号暗示历史补发、恰好一次投递或断线零丢失。

阶段演示：TUI 连入唯一后端，查看并修改允许的 ctx 配置，完成工具对话；断开再连接后重新获取状态；同时连接第二个 client，验证共享状态及独立订阅清理。

## 9. 编码落点与依赖约束

| 范围 | 建议模块 | 必须保持的约束 |
| --- | --- | --- |
| `packages/aurora_core/src/aurora_core/` | ids、registry、bootstrap、discovery、ctx、events、hooks、invocation、persistence、lifecycle | 不导入 bot、CLI、API 或模型 SDK；模块按行为形成后再拆分 |
| `packages/aurora_model_adapter/src/aurora_model_adapter/` | protocols、models、factories、adapters | 依赖 core；上层仅消费统一协议 |
| `packages/aurora_bot/src/aurora_bot/` | assembly、conversation、react、tools、multi_model、agents、mcp、resources | 装配入口保持薄；默认业务由插件实现；CLI/API 通过声明连接 |
| `packages/aurora_cli/src/aurora_cli/` | main、commands、config | 接收命令，不复制 ctx 或 bot 逻辑 |
| `packages/aurora_api/src/aurora_api/` | app、config、endpoints、contracts | 只提供明确的传输绑定，不导入 bot 实现 |
| `packages/aurora_client/src/` | ctx、transport、subscriptions、connection、generated | 共用 core ctx 身份与语义，不复制后端插件树 |
| `apps/aurora_tui/`、`apps/aurora_panel/` | 应用入口、视图、本地动作及偏好 | 共享 client；界面状态按需要留在本地 |
| `apps/docsite/`、`apps/landing/` | 页面、导航、静态资源、构建配置 | 静态构建独立于后端运行 |
| `scripts/`、`tests/` | 检查、契约生成、夹具、边界与集成用例 | 按需建立可重复入口，默认验证不依赖外部密钥 |

结构化存储服务的实际提供包由 D04 确定；表中的 persistence 仅表示 core 所需的持久化基础，不提前替 D04 选择完整数据库架构。

## 10. 验证与完成标准

### 10.1 验证分层

| 层次 | 重点覆盖 | 对应阶段 |
| --- | --- | --- |
| `tests/unit/` | ID 校验与冲突、ctx 可变值边界、通知、兼容判断、排序、模型转换、ReAct 终止、界面状态逻辑 | M0 起按任务添加 |
| `tests/contract/` | 实际稳定的插件接收接口、ModelClient、ctx 跨语言行为、HTTP/WS 公开数据、生成类型一致性 | M1 起按真实边界添加 |
| `tests/e2e/` | 插件发现、关闭及恢复、默认 bot、工具循环、客户端重连、多界面与扩展生命周期 | 各里程碑出口 |
| 人工冒烟 | 真实模型、终端键位/渲染/恢复、浏览器交互、静态站点导航 | M2 起按可用配置执行 |

网络与真实模型验证单独运行并记录结果；离线自动检查使用假模型、可控时钟、临时存储和本地服务夹具。测试验证外部行为与失败边界，不为占位文件或实现细节编写镜像测试。

### 10.2 检查入口建设顺序

1. M0.1 建立 Python 测试、Ruff 和包导入检查，明确工作区依赖安装方式。
2. M1 加入生命周期、落盘故障和插件装配集成检查。
3. M2 加入模型适配契约、默认 bot 离线端到端检查及独立真实模型冒烟入口。
4. M3 建立 TS 类型检查、client 测试、契约生成检查及 API/client 联调入口。
5. M4 为已实现应用添加独立 build 和必要的界面冒烟，最后汇总为工作区检查入口。

这些是待建设的命令入口，不表示当前仓库已有相应 npm scripts、测试配置或持续集成流水线。

### 10.3 单任务完成标准

- 任务列出的行为和失败路径可复现，必要的测试通过。
- 依赖方向、公共 ID、kind、实例定位及可选宿主行为符合基线。
- 本次需要确定的接口语义在代码类型、中文 docstring 和行为测试中一致。
- 新增异步任务、订阅、文件、连接或子进程具有对应释放路径。
- 仅生成和公开本任务需要的数据；外部接口覆盖敏感数据和错误路径的检查。
- 检查范围与改动相称；变更说明如需记录，统一写入 `docs/CHAGELOG.md`。
